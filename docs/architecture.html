The Unary Byte-Frame Law

Architecture

One law governs every callable in this repository: one explicit input, one explicit physical frame result. The tooling that signs, verifies, and consolidates is built as small typed arrows composed by make — and where the implementation falls short of the law, the gap is recorded in red, never papered over.

The law in brief

One Input, One Frame

T → Frame(output: X, error|effect: Y)

Every exposed callable — independent of language, file type, path, or generated status — is inventoried as a typed arrow with one explicit input and one explicit physical frame result. The frame is a typed product, not a tuple, Either, Try, or implicit exception: input, output, and error-or-effect are separately navigable coordinates.

  • Active-red honesty. The law's status is active red migration: it is specified in full while the enforcement implementation does not yet satisfy the law it enforces. Provisional and gap rows are recorded over pretense — a bounded census cannot be green while a shortcut remains.
  • Full lexical identity. No abbreviation, acronym, or fused expansion is an internal coordinate. Internally it is shapes/constraint/language, query/protocol/language, resource/description/framework — spellings like SHACL, SPARQL, gpg survive only as immutable external evidence on the far side of a registered bridge.
  • Bridges, registered. Anything whose protocol cannot be a lawful unary callable — git hooks, CI workflow steps — is a registered external bridge: it declares its findings in a header and delegates all policy to the typed tree.

The full law — semantic ancestry, build bootstrap boundary, normative boundary, explicit binding and observation, sealed self-hosting closure — is the authoritative document docs/unary-byte-frame-law.md (embedded below).

The Python realization

Leaves, Gates, Constants, Ledgers

The executable tree rooted at scripts/python/pylib admits exactly three leaf filenames, each carrying one public symbol:

LeafSymbolRole
value.py VALUE A constant leaf: one byte string or command tuple under config/constants/…. Identities are URNs of the form urn:silmaril:<colon-path>:v1.
library.py DEPENDENCY A gate leaf: the only place an external import may occur (import X as DEPENDENCY) under config/gate/external/…. Explicit spelling elsewhere is not admission.
process.py MAIN An arrow leaf: exactly one semantic application — one subprocess run of a command tuple, or one gated library call chain reading stdin bytes and writing stdout bytes — ending raise SystemExit(MAIN()).
  • The make envelope. Every target guards SILMARIL_PYTHON (absent → exit 64), runs with PYTHONDONTWRITEBYTECODE=1 and PYTHONPATH=src, writes stdout to $@.pending, stderr to $@.stderr, the exit status to $@.status, and promotes the artifact with an atomic mv only on success. Bytes in, bytes out, evidence on disk.
  • The ledgers. Every process.py owns a row in a committed process ledger (tests/fixtures/*_process_ledger.csv) declaring, among eleven columns, its semantic_application_count = 1. The runtime test suite is the enforcement oracle: it walks the tree and rejects loops, try/ except, prints, multiple symbols, and unregistered imports.
  • The gates in one place. Four composite targets gate the whole system, and CI runs them all:
export SILMARIL_PYTHON=$(command -v python3)
make -C scripts/python/pylib morphism-provenance-trust-manifest-check
make -C scripts/python/pylib morphism-provenance-commit-policy-default
make -C scripts/python/pylib morphism-ontology-consolidation-check
make -C scripts/python/pylib morphism-ontology-validation

The morphism family map

Two Pipelines

The families live under silmaril/sparky/morphism/… with mirrored constants and gates. Each step below is one process.py — one arrow, one semantic application — composed by make.

provenance / trust

  1. trust/manifest/extraction — fingerprints, policy classes, key files, identities out of the ontology turtle
  2. trust/manifest/render — the manifest document
  3. drift gate — byte-compare against the committed keys/trust-manifest.txt

provenance / commit

  1. commit/keyring/construction — ephemeral keyring from committed public keys
  2. commit/observation/header and commit/observation/verification — raw commit headers and gpg verification evidence
  3. commit/classification/* — signature/type, then good, attested, secure/shell, unsigned, unknown, bad/signature
  4. commit/record/merge — one classified record per commit
  5. commit/policy/{default, report, strict} — the exit-status gate

See Provenance for what the classes mean and how the server bridge uses them.

ontology / consolidation

  1. consolidation/source/discovery — enumerate basicttl/
  2. consolidation/document/normalization — per-document cleanup (illegal local names percent-encoded)
  3. consolidation/namespace/union/projection — one namespace union
  4. consolidation/{corpus, entity, statement}/tally — census counts
  5. five renders — consolidated/render, shapes/constraint/language/document/render, query/protocol/language/document/emission, geographic/query/protocol/language/document/emission, manifest/render
  6. sync gate — the five artifacts must byte-match ontology/; regeneration is the documented copy in ontology/README.md (embedded below)

ontology / validation

  1. document/parse — the consolidated graph parses
  2. shapes/conformance — shapes-constraint-language conformance over the consolidated graph
  3. queries/parse — the query library parses
  4. queries/execution — the executable queries run and return rows

External libraries enter only through gates: resource_description_framework_library and shapes_constraint_language_library.
