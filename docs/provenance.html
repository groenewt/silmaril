Commit Provenance

The Trust System

Every commit in this repository is classified against a trust model that lives in the ontology, is rendered into a generated manifest, and is enforced by a typed byte-frame pipeline — on your machine, in CI, and at the server gate. Nothing is taken on faith; everything is a coordinate.

Who signs

The Three Identities

Trusted signing keys are declared as individuals in basicttl/commit_signing_trust.ttl — the authoritative trust model — committed as armored public keys under keys/, and rendered into the generated trust manifest that the verifier consumes. CI fails if the manifest drifts from the ontology.

How verification works

The Typed Pipeline

Verification is not a shell script — it is a family of unary byte-frame morphisms under scripts/python/pylib, each one process reading bytes and writing bytes, composed by make (see Architecture). The chain:

  • Trust extraction. Fingerprint, policy class, key file, and identity are extracted from the ontology and rendered into keys/trust-manifest.txt. A check gate fails on any drift between the committed manifest and a fresh render.
  • Ephemeral keyring. The committed public keys are imported into a temporary GNUPGHOME created for the run — your personal GnuPG keyring is never read or written.
  • Observation. Each commit's headers and its gpg verification output are captured as byte documents.
  • Classification. Per-commit records are merged and classified into exactly one of the six classification verdicts below, keyed by signature type and by the signer's fingerprint against the manifest.
  • Policy. A policy morphism reads the classified stream and decides the exit status. The classified report is always emitted either way.

Classification verdicts

Class Meaning Default policy Strict policy
GOOD Valid OpenPGP signature by a fingerprint in the trust manifest pass pass
ATTESTED Signed by a listed fingerprint whose key file is absent — acknowledged, not verifiable pass, acknowledged fail
SSH SSH-signed commit — outside the OpenPGP trust chain pass, warned fail
UNSIGNED No signature at all pass, warned fail
UNKNOWN Signed by a key outside the trust manifest fail fail
BADSIG Signature present but cryptographically invalid — tampered content or forged header fail fail

Default hard-fails BADSIG and UNKNOWN; strict accepts GOOD only; the report target classifies without gating. Run the report against the exact revision being reviewed; a profile or public key alone does not prove a commit signature.

Quickstart

export SILMARIL_PYTHON=$(command -v python3)
make -C scripts/python/pylib morphism-provenance-commit-policy-default   # verify history
make -C scripts/python/pylib morphism-provenance-commit-policy-report    # classify only
make -C scripts/python/pylib morphism-provenance-commit-policy-strict    # GOOD-only gate
make -C scripts/python/pylib morphism-provenance-trust-manifest-check    # manifest <- trust model
bash scripts/install-git-hook.sh                                         # bridge hooks

The wolf at the gate

Server-Side Bridges

Git hooks cannot be lawful internal callables — their protocol is multi-argument with a stdin stream — so they are registered external bridges: short scripts in hooks/ that carry their typed findings in a header comment and delegate all policy to the typed tree.

  • remote-update (server side) — the decisive one. The typed tree and trust material are extracted from a trusted revision: the old ref value, which the incoming push cannot rewrite — never from the pushed tip. A force-push carrying a tampered commit is verified against the policy of the history it is trying to replace, classifies BADSIG or UNKNOWN, and the ref never moves. A push cannot smuggle in its own policy.
  • pre-push (client side) — every outgoing revision range runs the default commit policy before it leaves your machine.
  • pre-commit — blocks staged shell syntax errors and staged armored secret key material; warns when your signing configuration would classify UNSIGNED or SSH (set git config silmaril.requiresign true to upgrade warnings to failures).
  • CI — the same make targets run as workflow bridges on pushes to master/main and on pull requests: commit policy, trust-manifest drift gate, ontology consolidation sync gate, semantic validation gates.
